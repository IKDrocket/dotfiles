# ステアリングドキュメント管理スキル

新機能・大きな変更を、その場の思いつきではなくドキュメント駆動で進めるためのスキル。
「作成」「実装」「振り返り」の3モードを持つ。

## モードの決定

引数・会話内容から以下の順で決定する:

1. 引数に `create` / `作成` があれば **作成**、`implement` / `実装` があれば **実装**、`retrospective` / `振り返り` があれば **振り返り**
2. モード指定がない場合:
   - 「〜を作りたい」「〜機能を追加」など新しい機能の話をしていれば **作成**
   - 「続きをやって」「実装して」で、かつ `.steering/` に未完了タスク（`[ ]`）を含むディレクトリがあれば **実装**
   - 実装完了直後の文脈なら **振り返り**
3. それでも判断できない場合は、どのモードを実行するかユーザーに確認する

## モード 1: 作成（create）

新機能・大きな変更の開始時にステアリングドキュメントを作成する。

### 手順

1. Bash で `date +%Y%m%d` を実行して現在日付を取得する
2. 機能名を英語のケバブケースに変換する（例: "ユーザー認証" → `user-auth`）
3. 要件・設計を書く前に、関連する既存コードを調査する（Glob/Grep/Read）。
   既存の実装パターン・影響範囲を把握せずに設計を書かないこと
4. `.steering/[YYYYMMDD]-[name]/` ディレクトリに以下の3ファイルを作成する。
   テンプレートは `~/.claude/skills/steering/templates/` にある:
   - `requirements.md` — ゴール・ユーザーストーリー・制約・受け入れ基準
   - `design.md` — アーキテクチャ・技術選定・データ構造・API・除外スコープ
   - `tasklist.md` — 実装タスクのチェックリスト（依存関係順）
5. 作成前にセルフチェックを行い、満たしていない項目があれば修正する:
   - [ ] 受け入れ基準は「実行して確認できる」形で書かれているか（「使いやすい」等の曖昧表現がないか）
   - [ ] design.md は requirements.md の全機能要件をカバーしているか
   - [ ] タスクは依存関係順で、1タスクが1コミット相当の粒度になっているか
   - [ ] 除外スコープ（今回やらないこと）が明記されているか
6. 作成したドキュメントの要約をユーザーに提示し、**承認を得るまで実装に進まない**

## モード 2: 実装（implement）

`tasklist.md` の未完了タスクを順番に実行する。

### 手順

1. `.steering/` 内の最新ディレクトリ（ディレクトリ名の日付が最新）を探す。
   複数候補があり判断できない場合、または `.steering/` が存在しない場合は、対象をユーザーに確認する
2. `requirements.md` と `design.md` を読んで前提を把握し、`tasklist.md` の `[ ]` タスクを確認する
3. 最初の未完了タスクから**1つずつ**実装する。複数タスクをまとめて進めない
4. 各タスク完了ごとに:
   - テストやビルドが定義されているプロジェクトでは実行し、通ることを確認する
   - `tasklist.md` の該当行を `[x]` に更新する
5. 実装中に design.md と矛盾する事実が見つかった場合は、勝手に設計を変えず、
   ユーザーに報告して design.md を更新してから続行する
6. タスクが失敗して解決できない場合は、そこで停止して状況を報告する（無理に次のタスクへ進まない）
7. すべてのタスクが完了したらユーザーに報告し、振り返りモードを提案する

## モード 3: 振り返り（retrospective）

実装完了後に学びを記録する。

### 手順

1. `.steering/` 内の最新ディレクトリを探す
2. 実装中の実際の出来事（設計変更・ハマった点・想定外の工数）を思い出し、
   `tasklist.md` の末尾に振り返りセクションを追記する:

```markdown
## 振り返り

**完了日**: YYYY-MM-DD

### よかった点

- （実装で上手くいったこと）

### 改善点

- （次回に向けた改善点）

### 学んだこと

- （技術的・プロセス的な気づき）
```

3. 各項目には具体的な事実を書く。「順調だった」のような内容のない記述は書かない
4. ユーザーに内容を確認してもらい、追記があれば反映する
