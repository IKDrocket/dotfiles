# コミット / PR 支援スキル

変更内容を「後から履歴を読む人」に伝わる形でコミット・PR にまとめる。

## 大原則

- **コミット・プッシュはユーザーが明示的に依頼したときのみ**実行する
- 既存コミットは amend しない。修正は新しいコミットで行う
- `--no-verify` などフックを回避するオプションは使わない
- `.env`・認証情報・秘密鍵がステージに含まれていないか、コミット前に必ず `git status` / `git diff --staged` で確認する

## コミット手順

### 1. 変更の全体把握

```bash
git status
git diff            # 未ステージ分
git diff --staged   # ステージ済み分
git log --oneline -5  # 直近のメッセージスタイルを確認
```

差分を読まずにメッセージを書かない。ファイル名だけからメッセージを推測しない。

### 2. 論理単位への分割

1コミット = 1つの論理的変更にする。判断基準:

- 「このコミットだけ revert したい」場面が想像できる単位か
- 機能追加とリファクタリングが混ざっていないか → 混ざっていれば分割する
- 分割する場合は `git add <file>` / `git add -p` でステージを分ける

差分が小さく単一の目的なら1コミットでよい。無理に分割しない。

### 3. メッセージ作成

このリポジトリ・プロジェクトの既存スタイル（`git log` で確認）を最優先する。
スタイルが確立していない場合は Conventional Commits に従う:

```
<type>: <変更の要約（何を・なぜ）>
```

- type: `feat` / `fix` / `refactor` / `docs` / `test` / `chore`
- 要約は「なぜ」にフォーカスする。差分を見ればわかる「何をしたか」の羅列にしない

**例:**

| 悪い例 | 良い例 |
|--------|--------|
| `fix: コードを修正` | `fix: 空のタスクリストで実装モードがクラッシュする問題を修正` |
| `feat: ファイルを追加` | `feat: デプロイ失敗時に自動ロールバックするステップを追加` |
| `update README` | `docs: セットアップ手順に mise のインストールを追記` |

### 4. コミット実行と確認

コミット後に `git status` と `git log -1` で意図どおりのコミットになったことを確認する。

## PR 作成手順

### 1. 差分の全容把握

ベースブランチとの差分**全体**を確認する（最新コミットだけを見ない）:

```bash
git log main..HEAD --oneline
git diff main...HEAD --stat
```

### 2. PR 説明文の作成

以下のテンプレートに従う:

```markdown
## 概要

（この PR で何が変わるか 1〜3 文）

## 背景・理由

（なぜこの変更が必要か。関連 Issue があればリンク）

## 変更内容

- （主要な変更点を箇条書き）

## テスト

- （実行したテスト・動作確認の内容）

## 影響範囲・レビュー時の注意

- （破壊的変更・マイグレーション・レビューで特に見てほしい箇所）
```

### 3. PR 作成

`gh pr create` を使う。プッシュが必要な場合は必ずユーザーに確認してから行う。
